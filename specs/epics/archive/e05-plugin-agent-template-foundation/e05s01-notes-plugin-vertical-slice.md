# e05s01 — Notes Plugin Vertical Slice

## 1. Identity

- **Story ID:** e05s01
- **Epic:** e05 — Plugin and Agent Template Foundation
- **Type:** feat
- **Risk:** P0
- **Context:** domain, security, persistence, runtime, tools, and CLI
- **BCPs:** 8
- **Status:** passing
- **Requirement delta:** ADDED

## 2. User Story

As a Mia user, I want to install Notes for one Agent and ask that Agent to create, list, and read private notes so that I can add useful executable behavior without changing Mia Core or enabling it for every Agent.

## 3. Context

The released Agent model already persists `plugins`, but the field is inert. `AgentRuntimeFactory` constructs only filesystem, shell, and Delegation Tools. This tracer bullet proves the Plugin concept end to end with one bundled extension, one local install record, one explicit per-Agent enablement, three note capabilities, one Agent-owned data boundary, and the existing access/middleware pipeline.

## 4. Problem

Mia claims Plugins as its executable extension primitive but cannot install or execute one. Adding Notes directly to the built-in Tool list would deliver notes but would not prove install, enablement, ownership, or extension boundaries. Loading arbitrary third-party Python would introduce package and trust design before a concrete contract exists.

## 5. Goal

Deliver a complete offline journey: install the bundled Notes Plugin, enable it for Agent A, build Agent A with `note_create`, `note_list`, and `note_read`, execute those Tools through core policy, persist notes only under Agent A, and prove Agent B and Plugin-free Agents receive no Notes capability.

## 6. Non-Goals

- Remote registries, marketplace discovery, publishing, signing, or downloads.
- Arbitrary Python modules, dependency installation, or package isolation.
- Note edit, delete, search, tags, attachments, sync, or collaboration.
- Plugin configuration, disablement hardening, and full diagnostics beyond the minimum enable path; completed by e05s02.
- Mutable Plugin overlays for immutable built-in Agents; the proof uses persisted user-created Agents.
- Agent Template creation; completed by e05s03.
- Plugin Skills, hooks, workflows, providers, UI, channels, or background tasks.

## 7. Stakeholders

- Users who want local note assistance.
- Agent designers enabling capabilities selectively.
- Core maintainers responsible for Tool visibility, access, audit, and Session integrity.
- Future Plugin developers who need one concrete contract rather than a speculative SDK.

## 8. Dependencies

- Approved `specs/product/SCOPE_LATEST.yaml` and VISION-05.
- `Agent`, `AgentManager`, `AgentRuntimeFactory`, `AgentHarness`, `BaseTool`, and `ToolPipeline` contracts.
- Existing atomic Agent persistence and path-safe Agent homes.
- Existing Pydantic, Typer, pytest, Ruff, Mypy, and standard library only.

## 9. Assumptions

- Bundled Plugin code is trusted distribution code; e05 does not claim runtime sandboxing.
- Installation means explicit local activation of a bundled Plugin, not downloading code.
- Enabling Notes explicitly adds its manifest-declared Tools to that Agent's effective capability scope without mutating the Agent's base Tool list.
- Note IDs are generated by Mia and cannot contain user-controlled path components.
- Notes persist outside Session history under the owning native Agent home.
- Legacy-only projected Profiles cannot receive persistent Plugin configuration until saved as native Agents.

## 10. Constraints

- No new runtime or development dependency.
- Plugin IDs and manifest fields are strict, normalized, versioned, and secret-free.
- Plugin Tool names are globally unique at runtime; duplicates fail before provider execution.
- Every Plugin Tool declares an effect; undeclared or invalid effects fail closed as side-effecting or reject activation.
- Plugin Tools are present only when the Plugin is installed and enabled for the resolved Agent.
- Runtime composition occurs before the existing Agent capability and read-only filters.
- `tool_effects` includes Plugin Tools before `AccessPolicyMiddleware` is built.
- Existing Tool and event behavior is unchanged for Plugin-free Agents.
- Notes paths never derive from workspace `cwd`, user titles, or model-provided filenames.

## 11. Domain Model

- **Plugin Manifest:** validated description of one bundled executable extension, its version, and declared contributions.
- **Installed Plugin:** local explicit activation record for one bundled Plugin ID.
- **Enabled Plugin:** installed Plugin selected in one Agent definition.
- **Plugin Contribution:** a declared Tool built for one resolved Agent-owned data root.
- **Notes Plugin:** bundled Plugin contributing `note_create`, `note_list`, and `note_read`.
- **Note:** generated ID, title, content, and creation timestamp stored under one Agent.

## 12. Requirements

### ADDED: Bundled Plugin manifest and installation

Mia MUST expose one strict manifest for Plugin `notes`. A user MUST explicitly install it from the bundled catalog without network access. Unknown Plugin IDs, invalid manifests, and duplicate installed IDs MUST fail without modifying installation state.

### ADDED: Explicit per-Agent Notes enablement

A user MUST explicitly enable installed Plugin `notes` for one persisted non-built-in Agent. Enablement MUST persist the Plugin ID atomically; its strict manifest supplies the three declared Tool names to effective capability scope. It MUST NOT mutate the Agent's base Tool list, access level, full-access consent, delegation targets, credentials, another Agent, or existing Plugin data.

### ADDED: Notes Tool contribution

An enabled Notes Plugin MUST contribute `note_create`, `note_list`, and `note_read` to later Runs of the owning Agent. An Agent without enabled Notes MUST receive none of these Tools.

### ADDED: Agent-owned Notes storage

`note_create` MUST generate the note identity and atomically persist title/content under the resolved Agent's Plugin data boundary. `note_list` and `note_read` MUST access only that boundary. Agent B MUST NOT observe Agent A's notes through the Plugin.

### ADDED: Core-mediated execution

Notes Tools MUST pass through capability filtering, effect classification, access approval, permanent security rules, audit, cost, redaction, and truthful Tool result handling. `note_create` is side-effecting; `note_list` and `note_read` are non-mutating.

### ADDED: Fail-closed runtime composition

Missing installation, undeclared contribution, duplicate Tool name, invalid Tool effect, or unsafe Plugin data path MUST prevent Plugin activation before a provider can request its Tools. Mia MUST NOT silently omit policy or expose unrestricted behavior.

## 13. Non-Functional Requirements

- **Security:** Agent and note boundaries reject traversal; Tool input/output remains redacted; no credentials enter Plugin state.
- **Durability:** install, Agent enablement, and note creation are atomic; Session JSONL remains append-only and separate.
- **Compatibility:** Plugin-free Agents retain the same built-in Tool set, access policy, events, and CLI behavior.
- **Determinism:** all Plugin and Notes tests use temporary roots and `MockProvider` offline.
- **Performance:** installation and note listing perform bounded local filesystem work and no network calls.
- **Maintainability:** implement only the registry and contribution shape exercised by Notes.

## 14. Contracts

### Existing contracts preserved

- `Agent` remains strict and secret-free; built-ins remain immutable.
- `AgentManager` remains the only Agent persistence boundary.
- `AgentRuntimeFactory` remains the single native Tool/runtime composition root.
- `AgentHarness.prompt()` remains a headless async event stream.
- Every visible Tool executes through `ToolPipeline`.
- Existing Tool effects and unknown-Tool fail-closed behavior remain unchanged.

### New contracts

- A Plugin manifest declares one normalized Plugin ID, version, Tool names, and Tool effects.
- A Plugin manager owns bundled discovery, local installation records, Agent enablement, and contribution resolution.
- Enabling a Plugin is the explicit capability-expansion action and uses AgentManager atomic persistence.
- Notes Tool construction receives an Agent-owned data root from Mia Core; the model cannot select a filesystem path.
- Duplicate Tool names or undeclared contributions reject runtime construction.

## 15. Reason for Depth and Zoom-Out

- **Plugin manifest:** required because install and runtime contribution must validate the same identity, version, names, and effects at a trust boundary.
- **Plugin manager:** required because installation state, per-Agent enablement, and runtime contribution resolution must share one fail-closed source of truth instead of being reimplemented in CLI and runtime callers.
- **Notes Tool module:** required because three Tools share one Agent-owned persistence contract; it is the concrete proof, not a general storage framework.

`AgentRuntimeFactory` exists to compose all Tools and policy for `AgentRunner`, `ModeRuntime`, Delegation, CLI, and REPL. Its contracts are shared provider injection, Agent ownership, capability/effect filtering, middleware, and Session continuity. The story changes only Tool discovery before existing filtering; it does not create a second runtime root.

## 17. Acceptance Criteria

### Scenario SC-e05s01-P0-01: Notes installs locally

```gherkin
Given an isolated Mia home and no installed Plugins
When the user installs bundled Plugin notes
Then the installed registry contains exactly one validated notes entry
And no network or dependency installation occurs
And reinstalling it does not corrupt or duplicate state
```

### Scenario SC-e05s01-P0-02: Notes enables for one Agent

```gherkin
Given Notes is installed and Agents alpha and beta exist
When the user enables Notes for alpha
Then alpha persists Plugin notes and receives its manifest-declared Tool capabilities
And beta remains unchanged
And neither Agent's access level or full-access consent changes
```

### Scenario SC-e05s01-P0-03: Enabled Notes runs through core policy

```gherkin
Given alpha enables Notes under approval-required access
When alpha reads or lists notes
Then the non-mutating Tool can execute without side-effect approval
When alpha creates a note
Then side-effect approval is required
And permanent security, audit, cost, and redaction middleware still execute
```

### Scenario SC-e05s01-P0-04: Notes remain Agent-owned

```gherkin
Given alpha and beta both enable Notes
When alpha creates a note
Then alpha can list and read it
And beta cannot list or read it
And no note path is derived from the workspace, title, or content
```

### Scenario SC-e05s01-P0-05: Invalid contributions fail before execution

```gherkin
Given a missing installation, duplicate Tool name, invalid effect, or undeclared Tool
When Mia builds the Agent runtime
Then runtime construction rejects the Plugin contribution
And the provider receives no invalid Tool definition
And no Plugin Tool executes outside middleware
```

### Scenario SC-e05s01-P1-06: Plugin-free Agents remain compatible

```gherkin
Given an existing Agent has no enabled Plugins
When Mia builds and runs it
Then its Tool set, policy, event ordering, Session behavior, and Delegation behavior match e04
```

## 19. Risks and Mitigations

- **Capability expansion:** enablement could expose undeclared Tools. Mitigation: manifest allowlist, explicit Agent write, duplicate rejection, and existing policy filtering.
- **Effect misclassification:** Plugin writes could appear safe. Mitigation: strict declared effects and fail-closed unknowns with approval tests.
- **Cross-Agent data leak:** global Notes paths could mix data. Mitigation: core supplies a fixed Agent-home root and tests two Agents.
- **Partial state:** install or enable could fail after one write. Mitigation: validate first, then atomic writes through existing helpers.
- **Runtime regression:** factory changes affect direct, delegated, and compatibility Runs. Mitigation: PluginManager injection, empty default, and existing orchestration/delegation suites.
- **Premature SDK:** generic hooks could expand scope. Mitigation: only Notes-required manifest, Tool, install, and enable contracts are permitted.
